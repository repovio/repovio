# Implementation Plan: Notifications Redesign

**Branch**: `codex/003-notifications-redesign` | **Date**: 2026-11-09 | **Spec**: [spec.md](spec.md)

**Issue**: [#65](https://github.com/repovio/repovio/issues/65)

**Input**: Feature specification from `specs/003-notifications-redesign/spec.md`.

## Summary

Consolidate notification breadcrumbs and Querry Kit actions using the existing `LayoutPage` action slot. Replace the
channel creation form with a four-step wizard. Repair browser-push enrollment and delivery accuracy, then move device
controls into a navbar popover with five recipient-scoped history entries. Keep administrative delivery history separate.
Implementation and local verification are complete except the explicit live-push/physical-click acceptance gates.
Progress and remaining evidence requirements are recorded in [tasks.md](tasks.md) and [quickstart.md](quickstart.md).

## Technical Context

**Language/Version**: TypeScript with the existing compiler aliases; Node.js 26.13.0; pnpm 11.28.9.

**Primary Dependencies**: Nuxt 4 SPA, Vue, Nuxt UI, Pinia, Querry Kit, NestJS/Fastify, Zod, Prisma, web-push,
and the existing Vite PWA/Workbox setup. Preserve manifest ranges.

**Storage**: Existing PostgreSQL notification models. Add nullable recipient attribution to browser Delivery Attempts
plus stable target identity with compatible migrations; no inbox or read-state tables.

**Testing**: Existing API Jest tests, web Vitest tests, Playwright notification/PWA suites, shared-schema tests,
and canonical formatting/documentation/lint/type checks.

**Target Platform**: Authenticated web SPA, responsive desktop/mobile; real Web Push on supported secure-context browsers.

**Project Type**: Existing pnpm/Nx web application and API monorepo.

**Performance Goals**: Fetch history lazily on popover opening, capped at five deliveries with deterministic ordering;
no per-route background history requests or unbounded attempt loading. Browser activation wait bounded to 15 seconds.

**Constraints**: Read-only provider integrations; database-enforced user/Repository visibility; encrypted push secrets;
no secrets in review summaries; no automatic permission prompt; English/German parity; unchanged admin-history gate.

**Scale/Scope**: Two table routes, one channel dialog workflow, navbar integration, push lifecycle, minimal personal-history
API/schema/persistence support, and focused regression coverage. No provider or toolchain migration.

**Structure Decision**: Reuse `LayoutPage`, `CommonTablePopoverTrigger`, existing typed table/composable patterns and
notification module. Keep route files focused on composition; named wizard steps own destination/events/review sections.
Use a dedicated personal-history projection rather than relaxing the admin Delivery DTO or CASL permissions.

## Phase 1: Design

See [data-model.md](data-model.md), [contracts/notifications.md](contracts/notifications.md), and
[quickstart.md](quickstart.md). Implementation order for task generation:

1. Reproduce enrollment failure safely; add focused failing regressions for worker readiness and server enrollment.
2. Repair lifecycle and expired-target attempt recording; add safe authenticated enrollment lookup and account cleanup.
3. Add nullable attempt recipient attribution and the restricted five-entry personal projection with migration tests.
4. Consolidate route-owned toolbars; keep both Querry Kit table bindings and admin gates intact.
5. Introduce wizard step validation, masked review, stale-preview protection, and existing edit preservation.
6. Integrate the navbar popover, remove the old banner, and add locale/browser acceptance coverage.
7. Complete focused and affected checks, production-worker validation, and an authorized real push smoke test.

No new dependency is expected. One focused `repovio` Changeset accompanies the later substantive implementation commit,
only if a commit is requested. Update the AST graph with source changes and retain only tracked `graph.json` output.

## Complexity Tracking

No additional architecture layer or constitutional exception is needed. The additive attempt attribution field is a
direct dependency of personal history: existing subscription foreign keys become null when a device is deleted.
