اس صفحے کی PAT/OAuth ہدایات ہر مخزن کا ویب ہک استعمال کرتی ہیں۔ GitHub App کنکشن ایک مرکزی ویب ہک اور ایپ مکالمے سے
ترتیب پاتے ہیں۔

Repovio OAuth یا ذاتی رسائی ٹوکن (PAT) کے ذریعے فراہم کنندہ کے اکاؤنٹس کو جوڑتا ہے۔ OAuth دستیاب ہوتا ہے جب کم از کم ایک
فراہم کنندہ OAuth کلائنٹ کنفیگر ہوتا ہے۔ بغیر کسی ترتیب شدہ OAuth کلائنٹس کے، فراہم کنندہ اکاؤنٹ اسکرین صرف PAT تصدیق
پیش کرتی ہے۔ Repovio اپنے صرف پڑھنے کے لیے فراہم کنندہ APIs کے لیے یا تو نتیجے کی سند کا استعمال کرتا ہے اور اسے
PostgreSQL پر لکھنے سے پہلے انکرپٹ کرتا ہے۔

<a id="register-oauth-applications"></a>

## OAuth درخواستیں رجسٹر کریں۔

ہر فراہم کنندہ مثال کے لیے ایک OAuth ایپلیکیشن رجسٹر کریں جسے Repovio سے منسلک ہونا چاہیے۔ ہر درخواست کے اندراج میں
`OAUTH_CALLBACK_URL` سے درست کال بیک URL سیٹ کریں۔ مقامی تنصیب کے لیے ڈیفالٹ
`http://localhost:3001/api/v1/provider-accounts/oauth/callback` ہے۔

API ماحول میں کلائنٹ آئی ڈی اور کلائنٹ سیکریٹ کو ترتیب دیں، کبھی بھی ویب ایپلیکیشن یا گٹ میں:

```dotenv
OAUTH_CALLBACK_URL=https://repovio.example.com/api/v1/provider-accounts/oauth/callback
GITHUB_OAUTH_CLIENT_ID=...
GITHUB_OAUTH_CLIENT_SECRET=...
GITLAB_OAUTH_BASE_URL=https://gitlab.example.com
GITLAB_OAUTH_CLIENT_ID=...
GITLAB_OAUTH_CLIENT_SECRET=...
FORGEJO_OAUTH_BASE_URL=https://forgejo.example.com
FORGEJO_OAUTH_CLIENT_ID=...
FORGEJO_OAUTH_CLIENT_SECRET=...
```

صرف ان فراہم کنندگان کو ترتیب دیں جن کی اس تنصیب کی ضرورت ہے۔ کلائنٹ IDs اور رازوں کو ہمیشہ جوڑوں کے طور پر کنفیگر کیا
جانا چاہیے۔ `GITLAB_OAUTH_BASE_URL` انسٹال کردہ OAuth ایپلیکیشن کے لیے واحد GitLab مثال کی شناخت کرتا ہے۔ Forgejo کو ایک
واضح بنیادی URL کی ضرورت ہے جب اس کا OAuth کلائنٹ کنفیگر ہو۔

<a id="read-scopes"></a>

## دائرہ کار پڑھیں

درخواست کو رجسٹر کرتے وقت ان اسکوپس کا استعمال کریں:

- GitHub: `repo security_events`۔ اس سے پہلے کہ Repovio سیکیورٹی الرٹس کو پڑھ سکے موجودہ OAuth اکاؤنٹس کو دوبارہ مجاز
  ہونا چاہیے۔
- GitLab: `read_api read_user`۔

عمدہ GitHub ذاتی رسائی ٹوکنز کو Dependabot الرٹس، کوڈ سکیننگ الرٹس، اور خفیہ سکیننگ الرٹس تک رسائی کی ضرورت ہوتی ہے۔
GitLab سیکیورٹی الرٹ رسائی اضافی طور پر مثال کے لائسنس اور ٹوکن کے مالک کے پروجیکٹ کے کردار پر منحصر ہے۔ غیر دستیاب الرٹ
کی قسمیں دیگر ریپوزٹری سنکرونائزیشن اسکوپس کو ناکام کیے بغیر دکھائی جاتی ہیں۔

- Forgejo: `read:repository`۔
- Gitea: Gitea فراہم کنندہ اکاؤنٹ فارم میں پڑھنے کی رسائی کے ساتھ ایک ذاتی رسائی ٹوکن ترتیب دیں، بشمول مثال کے طور پر
  بنیادی URL۔ Repovio فی الحال مشترکہ Gitea OAuth کلائنٹ پیش نہیں کرتا ہے کیونکہ ہر خود میزبان مثال کو اپنی درخواست کے
  اندراج کی ضرورت ہوتی ہے۔

Repovio کے اڈاپٹر صرف توثیق، دریافت، ورک فلو سنکرونائزیشن، اور ویب ہک کی تصدیق کو ظاہر کرتے ہیں۔ وہ فراہم کنندہ کے وسائل
کو تخلیق، اپ ڈیٹ، ڈسپیچ، دوبارہ چلانے، منسوخ یا حذف نہیں کرتے ہیں۔ OAuth کلائنٹ کے راز API ماحول میں رہتے ہیں، اور فراہم
کنندہ کے ٹوکنز Repovio API کے ذریعے کبھی واپس نہیں کیے جاتے ہیں۔

## GitLab کنکشن کا دورِ حیات

اوپر دیے گئے درست callback URL اور صرف پڑھنے کے scopes کے ساتھ ایک خفیہ GitLab OAuth ایپ رجسٹر کریں۔ کلائنٹ secret کو
API ماحول میں رکھیں۔ صرف ترتیب دیا گیا GitLab instance اس ایپ کو استعمال کر سکتا ہے؛ دوسرے instance کے لیے موزوں
deployment configuration درکار ہے۔

نئے فراہم کنندہ اکاؤنٹ کے لیے **فراہم کنندہ شامل کریں**، GitLab اور OAuth منتخب کر کے رضامندی مکمل کریں۔ موجودہ GitLab
کنکشن کے لیے **GitLab OAuth سے جڑیں** منتخب کریں تاکہ اسے اسی جگہ تبدیل کیا جا سکے۔ زیرِ انتظام OAuth کنکشن میں **دوبارہ
اجازت دیں** دستیاب ہے۔ تبدیلی GitLab صارف کی عددی ID سے منسلک ہوتی ہے؛ بعد کی اجازت اسی صارف سے ہونی چاہیے، چاہے اس کا
صارف نام بدل جائے۔ فراہم کنندہ اکاؤنٹ کی ID، موجودہ نام اور فعال حالت، زیرِ نگرانی repositories، رکنیتیں، ترتیب اور
تاریخ محفوظ رہتی ہیں۔ رضامندی منسوخ ہونے یا ناکام ہونے پر موجودہ کنکشن نہیں بدلتا۔

جن موجودہ کنکشنز میں refresh metadata محفوظ نہیں، انہیں ایک بار نئی اجازت درکار ہے۔ Repovio ان پرانے OAuth tokens اور
PAT میں فرق نہیں کر سکتا، اس لیے اپ گریڈ انہیں خودکار طور پر نیا نام نہیں دیتا یا تبدیل نہیں کرتا۔

<a id="gitlab-token-recovery"></a>

## Token کی گردش اور بحالی

Repovio access اور refresh tokens کو ایک ساتھ خفیہ کرتا ہے اور 60 سیکنڈ یا کم وقت باقی رہنے پر access token خودکار طور
پر نیا کرتا ہے۔ ہر کامیاب گردش پچھلے جوڑے کی جگہ لیتی ہے۔ `invalid_grant` کے ساتھ refresh مسترد ہونے پر کنکشن کو دوبارہ
اجازت درکار نشان زد کیا جاتا ہے اور کامیاب اجازت تک خودکار کوششیں رک جاتی ہیں۔ **دوبارہ اجازت دیں** استعمال کریں؛ کنکشن
حذف کر کے دوبارہ بنانے کی ضرورت نہیں۔

نیٹ ورک کی خرابیاں، timeout، rate limits اور سرور کی ناکامیاں موجودہ دوبارہ کوشش اور وقفے کے طریقے استعمال کرتی ہیں۔ گم
شدہ کلائنٹ ترتیب بحال کریں؛ کلائنٹ شناخت بدلنے پر نئی اجازت چاہیے، اور مختلف instance مسترد ہوتا ہے۔ اسناد یا فراہم
کنندہ کی خام خرابیاں کبھی نہیں دکھائی جاتیں۔ اگر GitLab tokens بدل دے مگر جواب کھو جائے یا database commit ناکام ہو تو
پرانے tokens پہلے ہی غیر مؤثر ہو سکتے ہیں۔ بحالی کے لیے دوبارہ اجازت دیں؛ PostgreSQL اور GitLab اس عمل کو ایک ہی ناقابلِ
تقسیم commit میں مکمل نہیں کر سکتے۔

<a id="gitlab-oauth-rollout"></a>

## اجرا اور واپسی

پہلے اضافی کالموں والی database migration لاگو کریں، پھر API اور ویب کے مطابق ورژن deploy کریں۔ ایپلیکیشن واپس کرتے وقت
نئے کالم برقرار رکھیں۔ پرانے ورژن GitLab OAuth tokens خودکار طور پر refresh نہیں کرتے اور واپسی GitLab کے منسوخ کردہ
tokens کو بحال نہیں کر سکتی۔
