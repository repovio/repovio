Инструкции PAT/OAuth на этой странице используют вебхуки отдельных репозиториев. Подключения GitHub App используют
единый вебхук и настраиваются через диалог приложения.

Repovio подключает учетные записи поставщиков через OAuth или токен личного доступа (PAT). OAuth доступен, если настроен
хотя бы один клиент OAuth провайдера. Без каких-либо настроенных клиентов OAuth экран учетной записи провайдера
предлагает только аутентификацию PAT. Repovio использует полученные учетные данные только для своих API-интерфейсов
поставщика, доступных только для чтения, и шифрует их перед записью в PostgreSQL.

<a id="register-oauth-applications"></a>

## Регистрация приложений OAuth

Зарегистрируйте одно приложение OAuth для каждого экземпляра провайдера, к которому должен подключиться Repovio.
Установите точный URL-адрес обратного вызова из `OAUTH_CALLBACK_URL` при каждой регистрации приложения. Для локальной
установки по умолчанию используется `http://localhost:3001/api/v1/provider-accounts/oauth/callback`.

Настройте идентификатор клиента и секрет клиента в среде API, а не в веб-приложении или Git:

```dotenv
OAUTH_CALLBACK_URL=https://repovio.example.com/api/v1/provider-accounts/oauth/callback
GITHUB_OAUTH_CLIENT_ID=...
GITHUB_OAUTH_CLIENT_SECRET=...
GITLAB_OAUTH_BASE_URL=https://gitlab.example.com
GITLAB_OAUTH_CLIENT_ID=...
GITLAB_OAUTH_CLIENT_SECRET=...
FORGEJO_OAUTH_BASE_URL=https://forgejo.example.com
FORGEJO_OAUTH_CLIENT_ID=...
FORGEJO_OAUTH_CLIENT_SECRET=...
```

Настройте только тех поставщиков, которые необходимы для этой установки. Идентификаторы клиента и секреты всегда должны
настраиваться парами. `GITLAB_OAUTH_BASE_URL` идентифицирует один экземпляр GitLab для установленного приложения OAuth.
Forgejo требуется явный базовый URL-адрес при настройке клиента OAuth.

<a id="read-scopes"></a>

## Области чтения

Используйте эти области при регистрации приложения:

- GitHub: `repo security_events`. Существующие учетные записи OAuth должны быть повторно авторизованы, прежде чем
  Repovio сможет читать предупреждения безопасности.
- GitLab: `read_api read_user`.

Детализированным токенам личного доступа GitHub требуется доступ для чтения к оповещениям Dependabot, оповещениям о
сканировании кода и оповещениям о секретном сканировании. Доступ к оповещениям безопасности GitLab дополнительно зависит
от лицензии экземпляра и роли в проекте владельца токена; недоступные типы оповещений отображаются без сбоев в других
областях синхронизации репозитория.

- Forgejo: `read:repository`.
- Gitea: настройте личный токен доступа с доступом на чтение в форме учетной записи поставщика Gitea, включая базовый
  URL-адрес экземпляра. Repovio в настоящее время не предлагает общий клиент Gitea OAuth, поскольку для каждого
  локального экземпляра требуется собственная регистрация приложения.

Адаптеры Repovio предоставляют только проверку, обнаружение, синхронизацию рабочих процессов и проверку
веб-перехватчика. Они не создают, не обновляют, не отправляют, не перезапускают, не отменяют и не удаляют ресурсы
поставщика. Секреты клиента OAuth остаются в среде API, а токены поставщика никогда не возвращаются API Repovio.

<a id="gitlab-connection-lifecycle"></a>

## Жизненный цикл подключений GitLab

Зарегистрируйте конфиденциальное OAuth-приложение GitLab с точным URL обратного вызова и правами чтения, указанными
выше. Храните секрет клиента в окружении API. Это приложение может использовать только настроенный экземпляр GitLab; для
другого экземпляра нужна соответствующая конфигурация развертывания.

Для новой учетной записи провайдера выберите **Добавить провайдера**, GitLab и OAuth и подтвердите согласие. Для
существующего подключения GitLab выберите **Подключить через GitLab OAuth**, чтобы преобразовать его на месте.
Управляемые OAuth-подключения предлагают **Повторную авторизацию**. Преобразование привязывает числовой ID пользователя
GitLab; последующие авторизации должны использовать того же пользователя, даже если его имя изменилось. Сохраняются ID,
текущее имя и состояние включения учетной записи провайдера, отслеживаемые репозитории, членство, настройки и история.
Отмена или ошибка согласия не меняет существующее подключение.

Существующие подключения без сохраненных метаданных обновления требуют одной новой авторизации. Repovio не может
отличить эти старые OAuth-токены от PAT, поэтому обновление приложения не меняет их классификацию и не преобразует
автоматически.

<a id="gitlab-token-recovery"></a>

## Ротация токенов и восстановление

Repovio шифрует токены доступа и обновления вместе и автоматически обновляет токен доступа, когда остается не более 60
секунд. Каждая успешная ротация заменяет предыдущую пару. Отказ обновления с `invalid_grant` помечает подключение как
требующее повторной авторизации и прекращает автоматические попытки до ее успеха. Используйте **Повторную авторизацию**;
удалять и создавать подключение заново не требуется.

Сетевые ошибки, тайм-ауты, ограничения частоты и ошибки сервера используют существующие повторы с задержкой.
Отсутствующую конфигурацию клиента нужно восстановить; изменение идентификатора клиента требует повторной авторизации, а
несовпадающий экземпляр отклоняется. Учетные данные и необработанные ошибки провайдера не показываются. Если GitLab
обновил токены, но ответ потерян или фиксация в базе данных завершилась ошибкой, старые токены уже могут быть
недействительны. Для восстановления повторите авторизацию: PostgreSQL и GitLab не могут атомарно зафиксировать эту
операцию.

<a id="gitlab-oauth-rollout"></a>

## Развертывание и откат

Сначала примените добавочную миграцию базы данных, затем разверните согласованные версии API и веб-приложения. При
откате приложения сохраните добавленные столбцы. Старые версии не обновляют OAuth-токены GitLab автоматически, а откат
не восстанавливает токены, уже аннулированные GitLab.
